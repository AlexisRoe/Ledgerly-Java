Lesson 25: Validation and error handling

← All lessons · About 14 minutes. Builds on Lesson 24.

The one idea

Invalid requests are caught at two layers, and a third piece turns every failure into one error format.

LayerCatchesIn Ledgerly
Contract (Bean Validation)Wrong shape: missing field, too longGenerated @NotNull @Size(min = 1, max = 200) on merchant, from openapi.yaml
Domain rulesBusiness rulesExpense.validMerchant throws InvalidInput("merchant", ...)
Error handlerTranslating exceptions into responses@RestControllerAdvice classes

Bean Validation. @Valid on a @RequestBody parameter validates its constraints; a failure raises MethodArgumentNotValidException. Constraints placed directly on method parameters trigger method validation and HandlerMethodValidationException (Spring: validation). The generated createExpense already has @Valid @RequestBody, which you saw in Lesson 22.

Central error handling. An @ExceptionHandler method handles exceptions thrown by controllers; in a @ControllerAdvice class it applies across controllers (Spring: exceptions). It can return a ProblemDetail, the RFC 9457 error body with media type application/problem+json (Spring: error responses).

Read real code

// ExpenseDomainExceptionHandler.java
@RestControllerAdvice
@Order(Ordered.HIGHEST_PRECEDENCE)
class ExpenseDomainExceptionHandler {
    @ExceptionHandler(ExpenseException.class)
    ResponseEntity<ProblemDetail> handle(ExpenseException e) {
        ProblemDetail problem = switch (e) {      // Lesson 16: sealed, exhaustive
            case InvalidTransition t -> problems.create(ErrorCatalogue.EXPENSE_INVALID_TRANSITION, ...);
            case InvalidInput i      -> problems.create(ErrorCatalogue.VALIDATION_FAILED, ..., List.of(new FieldViolation(...)));
            ...
        };
        return ResponseEntity.status(problem.getStatus()).body(problem);
    }
}
  • The use case just throws (Lesson 10). Nobody catches in between; the exception travels up to this advice, and the client receives a JSON problem with a stable code from ErrorCatalogue.
  • ProblemExceptionHandler extends ResponseEntityExceptionHandler for the framework's own errors such as MethodArgumentNotValidException.
  • The same limit exists twice on purpose: maxLength: 200 in the contract and MAX_MERCHANT = 200 in Expense.
  • Extending: a new business rule means a new exception in the sealed ExpenseException hierarchy; the compiler then forces you to map it in this switch.
