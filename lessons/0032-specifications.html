Lesson 32: Specifications and dynamic queries

← All lessons · About 12 minutes. Builds on Lesson 31.

The one idea

A Specification is a reusable predicate over an entity, built with the JPA Criteria API; combine them with and/or and pass the result to a repository (Spring Data: Specifications). In lambda form it has three parameters:

Specification<Expense> hasStatus(ExpenseStatus status) {
    return (root, query, cb) -> cb.equal(root.get("status"), status);
}   // root = the entity, cb = CriteriaBuilder building the condition

This is how optional filters work without a method per combination (findByStatusAndCategoryAndClaimant... would explode).

Read real code

ExpenseSpecifications has one small factory per filter (inTeam, hasStatus, claimedBy, incurredFrom...). ExpenseFilters.build composes them:

Specification<Expense> spec = inTeam(teamId);                 // always first
UserId claimant = actor.role().includes(Role.APPROVER) ? f.claimantId() : actor.id();
if (claimant != null) spec = spec.and(claimedBy(claimant));
if (f.status() != null) spec = spec.and(hasStatus(f.status()));
if (f.category() != null) spec = spec.and(hasCategory(f.category()));
...
return spec;
  • null means "no filter on this" (the @Nullable fields of the query record, Lesson 8).
  • Security lives in the query. It always starts with inTeam, and a plain MEMBER is forced to their own expenses "whatever claimant they ask for".
  • The paged list and the CSV export both call ExpenseFilters.build, so "they can never disagree".
  • ListExpenses then runs expenses.findAll(spec, PageRequest.of(page, size, sort)). The repository declares that method itself (Lesson 24) instead of extending JpaSpecificationExecutor, so there is still no un-scoped finder.
Extending: a new filter is one new factory in ExpenseSpecifications, one nullable field in Filter, one if in build, plus the query parameter in openapi.yaml (Lesson 22).
