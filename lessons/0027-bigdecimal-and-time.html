Lesson 27: BigDecimal and time

← All lessons · About 12 minutes. Builds on Lesson 26.

The one idea

Money and dates are where backends go wrong. Two habits keep Ledgerly safe.

BigDecimal for money. A BigDecimal is an integer plus a scale (digits after the point). Create it from a String: new BigDecimal(0.1) is actually 0.1000000000000000055..., because a double carries binary error. equals needs "both the numerical value and representation to be the same", so 2.0 and 2.00 are not equal, but compareTo says 0. setScale(2) without a rounding mode throws if digits would be lost (BigDecimal API).

new BigDecimal("2.0").equals(new BigDecimal("2.00"));       // false
new BigDecimal("2.0").compareTo(new BigDecimal("2.00"));   // 0
new BigDecimal("2.345").setScale(2, RoundingMode.HALF_UP); // 2.35
new BigDecimal("2.345").setScale(2);                       // ArithmeticException

That is why Money (Lesson 8) ends its constructor with amount = amount.setScale(digits): after normalising the scale, record equals works, which MoneyTest checks (10.0 equals 10.00). In the database it is amount numeric(19,4) (V1__expenses.sql).

Inject a Clock. java.time has Instant (a moment on the timeline), LocalDate (a date without time or zone) and Clock, an alternative to the system clock. Calling now() directly ties code to the real time; a Clock parameter lets tests use "a fixed clock, where time does not change" (Oracle: Clock, overview).

// CreateExpense.java, via constructor injection (Lesson 19)
private final Clock clock;
Expense expense = Expense.draft(..., c.incurredOn(), ..., clock);   // LocalDate: when it was spent
events.publishEvent(new ExpenseEvent.Created(..., clock.instant())); // Instant: when it happened

Expense.draft uses the clock to refuse a future date. In tests MutableClock extends Clock and has advance(Duration) for expiry and lockout tests.
