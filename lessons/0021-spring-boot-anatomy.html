Lesson 21: Anatomy of the Spring Boot app

← All lessons · About 12 minutes. First lesson of the Spring Boot track; syntax is done in Lessons 1 to 20.

The one idea

@SpringBootApplication combines three things: @EnableAutoConfiguration, @ComponentScan "on the package where the application is located", and @SpringBootConfiguration (Spring Boot docs). LedgerlyApplication sits in com.ledgerly, so scanning finds every @RestController, @Service and @Component below it (Lesson 19). main calls SpringApplication.run(...) and that is the whole entry point.

How the repo is laid out

Each module (expenses, receipts, teams, identity, ...) has a small public surface at the top (facade interface, records, events) and an internal folder with four layers:

FolderHoldsExample
internal/webControllers, error handlers, mappersExpensesController
internal/applicationUse cases: one class per actionCreateExpense, ListExpenses
internal/domainEntities, rules, domain exceptionsExpense, InvalidInput
internal/infrastructureRepositories, adapters to the outsideExpenseRepository

One request, end to end

POST /api/v1/teams/{teamId}/expenses
  -> ExpensesController.createExpense(...)       web: parse the request
  -> CreateExpense.execute(command, key)          application: orchestrate, @Transactional
  -> Expense.draft(...)                           domain: rules, builds the entity
  -> ExpenseRepository.save(expense)              infrastructure: writes to the database
  <- ResponseEntity 201 Created                   web: map the answer

The controller's own class comment says it: "Thin: parse, call one use case, map the answer." Rules live in the domain, orchestration in the use case, HTTP details in the controller. When you extend the backend, ask first: which layer is this change about?

For the module rules and reasons see CONCEPT.md and the ADRs.
