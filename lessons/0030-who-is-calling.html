Lesson 30: Who is calling? Authentication in code

← All lessons · About 12 minutes. Builds on Lesson 29.

The one idea

After the JWT is validated, Spring Security stores the result where any code on the same thread can read it. The SecurityContextHolder holds a SecurityContext, which holds an Authentication with a principal, credentials and authorities. By default it uses a ThreadLocal (Spring Security: authentication architecture). For a JWT the object is a JwtAuthenticationToken, and its name maps to the token's sub claim (JWT resource server).

Read real code

// shared/security/CurrentUser.java
public interface CurrentUser { UserId id(); }

// shared/security/JwtCurrentUser.java
@Component
public class JwtCurrentUser implements CurrentUser {
    public UserId id() {
        Authentication authentication = SecurityContextHolder.getContext().getAuthentication();
        if (!(authentication instanceof JwtAuthenticationToken token)) {   // Lesson 16
            throw new Unauthenticated();
        }
        return new UserId(UUID.fromString(token.getToken().getSubject()));
    }
}
  • The only code that touches Spring Security's static holder is JwtCurrentUser. Every controller asks the CurrentUser interface (Lesson 11), as ExpensesController does with currentUser.id().
  • The user id is the validated token's subject, parsed into a UserId. It never comes from the request body, so a client cannot claim to be someone else.
  • Two different failures: 401 means not authenticated (Unauthenticated), 403 means authenticated but not allowed (Forbidden, Lesson 31).
  • Threads: the context is thread-bound. An @Async listener runs elsewhere, and Spring notes that ThreadLocals and logging context are not propagated to async listeners by default (Spring: events). That is why events such as ExpenseEvent carry actorId: they cannot ask who is logged in. Lesson 34 returns to it.
