Lesson 31: Authorization in layers

← All lessons · About 15 minutes. Builds on Lesson 30.

The one idea

Authentication says who; authorization says what they may do. Ledgerly checks it in three layers, each answering a different question.

LayerQuestionWhere
Filter chainIs there a valid token?anyRequest().authenticated() (Lesson 29)
Use caseIs the caller in this team, and with which role?ExpenseAccess.actor(teamId, userId)
DomainMay this role do this to this expense?Expense.requireDecider, isVisibleTo

Read real code

// ExpenseAccess.java
Actor actor(TeamId teamId, UserId userId) {
    return new Actor(userId, memberships.roleOf(teamId, userId).orElseThrow(NotFound::new));   // not a teammate: 404
}

// Actor.java  (Lesson 8)
public record Actor(UserId id, Role role) {}

// Role.java
public enum Role { MEMBER, APPROVER, OWNER;
    public boolean includes(Role other) { return compareTo(other) >= 0; } }

// Expense.java
private void requireDecider(Actor actor, Role minimum, Action action) {
    if (!actor.role().includes(minimum)) throw new NotAllowed("Role " + actor.role() + " may not " + action);
    if (actor.id().equals(claimantId))   throw new SelfDealing(action);   // no approving your own expense
}
public boolean isVisibleTo(Actor actor) {
    return actor.id().equals(claimantId) || actor.role().includes(Role.APPROVER);
}
  • The use case looks up the role and hands the domain an Actor; "the domain receives the role; it never looks it up". That keeps rules testable without a database (Lesson 26).
  • A non-member, or an expense they may not see, gets 404, not 403, so the existence of teams and expenses is not revealed. A teammate with too low a role gets a refusal (NotAllowed).
  • Role is an enum ranked by declaration order, so includes is one comparison (Lesson 4's enum).

Method security

@EnableMethodSecurity (on SecurityConfig) turns on @PreAuthorize: the expression is checked before the method runs, and a failed check throws AccessDeniedException, typically a 403 (Spring Security: method security). Ledgerly's controllers use a bean call:

@PreAuthorize("@teamAuthorization.anyOf(#teamId, 'OWNER')")
public ResponseEntity<AuditEventPage> listAuditEvents(UUID teamId, ...) { ... }

@teamAuthorization is the bean TeamAuthorization; #teamId is the method parameter. The bean reads the caller's role from the database on every call and throws NotFound (not a teammate) or Forbidden (wrong role). Used in AuditController and TeamsController.

Rule for extending: when you add an endpoint, decide the answer to "who may call this?" before writing it. Team-scoped? Start the use case with access.actor(...). Role-restricted? Add a rule in the domain or a @PreAuthorize. Then write a test for the forbidden case (see the owasp/ tests).
