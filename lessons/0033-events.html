Lesson 33: Events

← All lessons · About 13 minutes. Builds on Lesson 32.

The one idea

An event says "something has happened"; modules react without the publisher knowing who listens. Publish with ApplicationEventPublisher.publishEvent(...); receive with @EventListener on a bean method. By default listeners run synchronously: "the publishEvent() method blocks until all listeners have finished" (Spring: application events).

@TransactionalEventListener binds the listener to a transaction phase; the default is AFTER_COMMIT, and "if no transaction is running, the listener is not invoked at all" unless fallbackExecution = true (Spring: transaction-bound events). The point: do not announce a change that might still roll back.

Read real code

// CreateExpense.java, inside @Transactional execute(...)
events.publishEvent(new ExpenseEvent.Created(c.teamId(), view.id(), c.claimantId(), clock.instant()));

// ExpenseEvent.java
public sealed interface ExpenseEvent permits Created, Edited, Deleted, Submitted, ... {
    UUID eventId();   TeamId teamId();   ExpenseId expenseId();   UserId actorId();   Instant occurredAt();
    record Created(UUID eventId, TeamId teamId, ExpenseId expenseId, UserId actorId, Instant occurredAt) implements ExpenseEvent {}
}
  • Events are Lesson 15 and 8 combined: a sealed interface with record cases. ExpenseEvent lists everything that can happen to an expense.
  • They carry ids and field names only; "no amounts, merchants, notes or rejection reasons, which may be personal" (ADR 0001). They carry actorId because a listener on another thread cannot ask who is logged in (Lesson 30).
  • eventId is "stable across re-delivery", so a listener can tell it has already handled an event.
  • Time comes from the injected Clock (Lesson 27): occurredAt is when it happened, not when delivered.
  • Events vs. calls: ADR 0003 settles it: a module may call another's facade to ask it to change data; events are for reacting to something that already happened.
Extending: a new thing worth auditing means a new record in ExpenseEvent's permits list; the compiler then points at every exhaustive switch to update (Lesson 16), and you publish it from the use case.
