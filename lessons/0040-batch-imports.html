Lesson 40: Batch imports with Spring Batch

← All lessons · About 15 minutes. Builds on Lesson 39.

The one idea

Spring Batch runs large jobs reliably. A Job is a container of Steps; a step in chunk-oriented style has an ItemReader (one item per call, null at the end), an optional ItemProcessor, and an ItemWriter that receives a whole chunk. Items are read until the commit interval is reached, the chunk is written, and "the transaction is committed" (Spring Batch: chunk-oriented processing). So a failure rolls back only the current chunk; earlier chunks stay.

A JobInstance is the Job plus its identifying JobParameters. Each attempt is a JobExecution; a failed instance can be run again with the same parameters and resumes "from where you left off" (Spring Batch: domain). The JobRepository keeps this state in BATCH_* tables.

Read real code

ImportJobConfig builds the CSV import:

new StepBuilder("importStep", repository)
    .<RawRow, NewExpense>chunk(limits.maxBatchSize(), transactionManager)   // 100 per transaction
    .reader(importReader)        // FlatFileItemReader over the uploaded file in object storage
    .processor(processor)        // RawRow -> NewExpense, or throw RowRejected
    .writer(importWriter)        // expenses.createDrafts(team, user, items)  (the facade, ADR 0003)
    .faultTolerant()
    .skip(RowRejected.class).skip(FlatFileParseException.class)
    .skipLimit(limits.maxImportRows())
    .listener(importSkipListener)
    .build();
  • Bad rows are skipped and reported, up to a limit; anything else, such as a database failure, stops the job. The writer calls ExpensesFacade.createDrafts (Lesson 11), so imported rows get the same validation as API creates.
  • The beans marked @StepScope read jobParameters['storageKey'], teamId, userId through @Value: the job is generic, the parameters say which file and for whom.
  • ImportRunner starts it. Recall Lesson 34: @Async @TransactionalEventListener(AFTER_COMMIT) on(ImportQueued), as a tracked listener. run switches on the stored status ("QUEUED" starts, "FAILED" restarts, otherwise nothing: Lesson 4 and 16).
  • parameters(importId) marks only importId as identifying, so a restart finds the same JobInstance and "resumes a FAILED import from the last committed chunk: lines already imported are not read or written again".
  • Configuration (Lesson 36): spring.batch.job.enabled: false so jobs start only on an upload, not at start-up; initialize-schema: never because Flyway creates the Batch tables in V6__imports.sql (Lesson 24).
  • The user-visible status lives in the app's own import_jobs table, kept in step by ImportJobListener.
Extending: a new bulk job is a new Job bean with reader, processor, writer and skip policy; keep the writer going through the owning module's facade, and keep chunk and skip limits in LedgerlyLimits.
