Lesson 36: Configuration and profiles

← All lessons · About 14 minutes. Builds on Lesson 35.

The one idea

Behaviour that differs per environment lives in configuration, not code. Spring Boot reads application.yaml from the classpath, plus application-{profile}.yaml when that profile is active, and profile files override the base ones. Later sources override earlier ones; environment variables beat the files, and command-line arguments beat both (Spring Boot: externalized configuration). Environment variables use underscores: SPRING_CONFIG_NAME for spring.config.name. Activate a profile with spring.profiles.active (Spring Boot: profiles).

Read real code

# application.yaml (always)               # application-local.yaml (profile "local")
spring:                                    logging: { structured: { format: { console: "" } } }   # readable logs
  jpa:                                     ledgerly:
    hibernate: { ddl-auto: validate }        storage: { s3: { endpoint: http://localhost:8333, ... } }
management: { server: { port: 8081 } }       receipts: { clamav: { host: localhost, port: 3310 } }
  • application.yaml holds what is true everywhere (graceful shutdown, ddl-auto: validate, actuator on its own port). application-local.yaml adds developer conveniences. make run sets SPRING_PROFILES_ACTIVE=local; compose.yaml sets the same for the app container, plus SPRING_DATASOURCE_URL and LEDGERLY_STORAGE_S3_ENDPOINT (the environment form of ledgerly.storage.s3.endpoint).
  • Production refuses to start with missing secrets. ProductionEnvironmentCheck (Lesson 3's loop) runs when the prod profile is active and lists every missing property with its environment variable name. .env.example documents them; the real .env is git-ignored.
  • Tests override with @SpringBootTest(properties = "management.server.port=0") (Lesson 26); test properties have the highest precedence.

Typed configuration

Instead of scattered strings, bind a prefix to a record (Lesson 8). A single constructor means constructor binding; @DefaultValue supplies defaults (docs). Register it with @EnableConfigurationProperties and inject it like any bean (Lesson 19):

@Validated
@ConfigurationProperties("ledgerly.limits")
public record LedgerlyLimits(@DefaultValue("100") @Positive int maxPageSize, @DefaultValue("10MB") DataSize maxUploadSize, ...) {}

@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties(LedgerlyLimits.class)
class LimitsConfig {}

// used in ListExpenses: constructor-injected, then limits.maxPageSize()

Property ledgerly.limits.max-page-size binds to maxPageSize (relaxed binding: context-path binds to contextPath). The Boot page excerpt I read did not cover validation or Duration/DataSize conversion; the repo shows both in use (@Positive, "10MB", "2s" in ReceiptsProperties).

Extending: a new setting is a field with a safe default in a properties record, a mention in .env.example if it has no default, and a line in the required list if production must set it. Never read secrets with hard-coded strings.
