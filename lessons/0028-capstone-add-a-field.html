Lesson 28: Capstone, add a field end to end

← All lessons · About 15 minutes. Builds on Lesson 27.

The goal

You can now name every piece. This lesson is the map for the most common real task: add an optional projectCode to an expense. It is a guided checklist: read first, then (in a separate session, with me beside you) do it for real on a branch.

The checklist, in order

  1. Contract. In api/openapi.yaml, add projectCode (maxLength: 20) to CreateExpenseRequest, UpdateExpenseRequest and ExpenseResponse. Build: the generated request/response classes and validation (Lesson 22, 25) appear in target/generated-sources.
  2. Migration. Add a new file src/main/resources/db/migration/V11__expense_project_code.sql with alter table expenses add column project_code varchar(20);. V1 to V10 exist; Flyway applies versions in order (Lesson 24).
  3. Entity. Add private @Nullable String projectCode; to Expense, set it in the private constructor, add an accessor projectCode(). With ddl-auto: validate, the app refuses to start if column and field disagree.
  4. Rule. Add a validProjectCode beside validMerchant that throws InvalidInput("projectCode", ...) (Lesson 25). Domain rules live in the domain, even if the contract repeats the limit.
  5. Use cases and mapping. Carry the value through NewExpense/CreateExpense.Command, UpdateExpense, ExpenseView and ExpenseMapper (the controller stays thin, Lesson 22/23).
  6. Tests. A unit test for the rule (like MoneyTest) and an API test for the happy path and the 400 (Lesson 26). Run make verify (Docker running).
  7. Docs. Add a request to the Bruno collection if the behaviour is user-visible.
The order is a map, not a law: contract first because it generates the interface you implement; migration before entity because the schema check runs at startup; tests last but before you call it done.
