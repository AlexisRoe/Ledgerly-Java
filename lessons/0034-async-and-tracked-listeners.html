Lesson 34: Async and tracked listeners

← All lessons · About 14 minutes. Builds on Lesson 33.

The one idea

@EnableAsync plus @Async makes a method return immediately while it runs "in a task that has been submitted to a Spring TaskExecutor". Allowed returns: void, Future, CompletableFuture. For a void method an exception "is uncaught and cannot be transmitted" (by default just logged), and calling an @Async method on this runs synchronously because only proxy calls are intercepted (Spring: task execution), the same limit as Lesson 23.

The risk: with plain @Async + @TransactionalEventListener, a failing listener can lose the event. Spring Modulith's answer is @ApplicationModuleListener, a shortcut for @Async + @Transactional(propagation = REQUIRES_NEW) + @TransactionalEventListener. Its event publication registry writes a log entry in the same transaction as the business change, marks it complete when the listener succeeds, and leaves it open if the listener fails, so it can be re-delivered (Spring Modulith: events).

Read real code

// ScanReceipt.java line 62: upload commits, then the scan starts on another thread
@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void on(ReceiptUploaded event) { scan(event.receiptId()); }

// ExpenseDeletedCleanup.java: react to a deleted expense
@ApplicationModuleListener
void on(ExpenseEvent.Deleted event) { ... delete receipt rows and files ... }

// AuditListeners.java: one @ApplicationModuleListener per event type
@ApplicationModuleListener
void on(UserRegistered e) { audit.record(e.eventId(), "USER_REGISTERED", ...); }
  • The class comment of ScanReceipt describes the guarantee: Modulith stores a publication in the same transaction as the upload, completes it when the method returns normally, and re-delivers it after a restart if the scan did not finish. The receipt stays PENDING_SCAN meanwhile, which is why Expense.submit refuses while scans are pending (Lesson 5).
  • That is also why scan throws IllegalStateException when the scanner is unreachable (Lesson 13): "swallowing it would mark the event as handled".
  • application.yaml sets republish-outstanding-events-on-restart: true and EventMaintenance resubmits listeners that failed while the app kept running.
  • AuditListeners records the audit trail this way, idempotently on eventId, because delivery can happen twice. Write listeners so that running twice is harmless.
  • @Async listeners run on virtual threads here (spring.threads.virtual.enabled).
Extending: a new reaction is a new @ApplicationModuleListener method taking the event type. Make it idempotent, and let real failures throw so the registry can retry.
